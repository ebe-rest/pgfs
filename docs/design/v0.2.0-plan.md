## The decisions

### Decision 1: bring the FUSE binding in-house (retire the `vendor/Tmds.Fuse` submodule and fork)
- pgfs carries **its own minimal libfuse P/Invoke binding**. The submodule and the fork are retired.
- **Why in-house (in a form that holds up publicly, and to the author of Tmds.Fuse)**:
  1. pgfs ships **single-file self-contained** -> a separately managed dependency works against the packaging.
  2. Only **a small subset (~20 ops)** of the FUSE high-level API is used. On top of that there were already
     **pgfs-specific downstream patches** (`fuse_config.use_ino` / `fuse_get_context` / mount-option
     passthrough), so a fork was being maintained for the sake of a thin P/Invoke layer.
  3. v0.2.0 moves to **per-OS assemblies** -> the libfuse binding sits naturally in the `Pgfs.Fuse` layer (Linux/POSIX).
- libfuse's **C ABI is the interface** (it is only bound; no source is vendored). **Tmds.Fuse is credited**
  (NOTICES / history). There is no need to bring LGPL to the surface (the reasons above stand on their own).

### Decision 2: split Lib along the OS layers (retire `#if` in favour of assembly boundaries)
"Common in the parent, specific in the derived" is realized through **assembly boundaries**. **The OS layers
are named after the FS mechanism** (the Windows side is `Pgfs.Dokan`). Why: **other patterns than Dokan (WinFsp
and so on) should be comparable**, so each mechanism is a swappable assembly. The Linux side follows the same
approach as `Pgfs.Fuse` (the libfuse mechanism).

| Assembly | Responsibility | The tools that reference it |
|---|---|---|
| **`Pgfs.Core`** | The **PostgreSQL/SQL shared part**, independent of the OS and the mechanism: Pg / Api / Config / Models (Inode, Data, Chunk, Audit, **the canonical ACL = PgfsAcl and NameNormalizer**) / Logging / Utility. Zero `#if` | mkfs, mount, assign |
| **`Pgfs.Fuse`** | Linux (macOS later): **the in-house libfuse binding** plus the FUSE FileSystem implementation / the PosixAcl projection / the posix uname-gname resolver | mount |
| **`Pgfs.Dokan`** | Windows: **the Dokan binding** plus the Dokan FileSystem implementation / `win_attrs` / the Windows SID and ACL projection / WindowsUserResolver | assign |

- **Canonical versus projected**: **the canonical form** that goes into the database and the xattrs (PgfsAcl,
  name-based IDs) lives in Core, and **the projection onto the OS** (applying the POSIX mode, converting to a
  Windows SID) lives in each mechanism layer (exactly as designed in [permission-interop.md](permission-interop.md)).
- **What the naming implies**: `Pgfs.WinFsp` and the like can be added as siblings later and compared with
  Dokan. Where the mechanism-independent Windows-OS common parts (SID/ACL/attrs/`WindowsUserResolver`) live is
  **decided in point 3**: they share `Pgfs.Dokan` for now, and when WinFsp is added everything but
  `FileSystem.cs` is extracted into a thin `Pgfs.Windows` OS layer (YAGNI).

## The detailed design (in progress) - A: the Lib split

### The layering (as proposed)

```
  the tools (thin exes)
    mkfs.pgfs ───────────────────────────────────┐
    mount.pgfs ──▶ Pgfs.Fuse  (Linux/libfuse) ──┐ │
    assign.pgfs ─▶ Pgfs.Dokan (Windows/Dokan) ──┤ │
                                                ▼ ▼
  ┌──────────────────────────────────────────────────────────┐
  │                         Pgfs.Core                         │
  │   independent of the OS and the mechanism, the shared SQL  │
  │   part, zero #if                                           │
  │  Pg / Api (the inode, data and chunk SQL) / InodeCache / Mode │
  │  NotifyChannel / RemoteChangeInfo                          │
  │  Config (every POCO, the Loader, the Store, Schema, HelpText, Tool) │
  │  Models (Inode, Data, Chunk, Audit*, the canonical PgfsAcl) │
  │  Logging / Collections / Objects                           │
  │  Utility (PathParser, Retry, Json, Fn, String, NameNormalizer, │
  │           the shared part of ServiceResolver)              │
  └───────────────────────────┬──────────────────────────────┘
                              ▼
                        PostgreSQL (Citus optional)

  Specific to Pgfs.Fuse:  the libfuse binding (in-house) / FileSystem (FUSE) /
                          the PosixAcl projection / the posix UserResolver / the posix native ServiceResolver
  Specific to Pgfs.Dokan: the Dokan binding / FileSystem (Dokan) / win_attrs /
                          the Windows SID and ACL projection / WindowsUserResolver / the win native ServiceResolver

  External system dependencies (not bundled; the user provides them):
    Pgfs.Fuse  -> libfuse.so   (LGPL, linked dynamically through dlopen)
    Pgfs.Dokan -> the Dokan driver (installed separately)
```

The direction of the dependencies: **the tools -> the mechanism layer (Fuse/Dokan) -> Core -> PostgreSQL**.
Core knows nothing above it.

### Where each file goes (settled, audited against the actual files)

The settled destinations after actually enumerating `src/lib/src` plus `src/{mkfs,mount,assign}/src` and
checking them off (build outputs excluded).

- **Pgfs.Core** (everything OS-independent in the current Lib):
  `AppInfo.cs` / `Api/{Api,Mode,InodeCache,NotifyChannel,RemoteChangeInfo}` /
  `Collections/{FirstList,RichDictionary,ComparerToEqualityComparer}` /
  `Config/*` (every POCO plus `ConfigLoader` plus `ConfigStore` plus `Schema` plus `HelpText` plus `Field` plus `Tool` plus `SaveTarget`) /
  `Logging/{ILogger,Instance,Logger,LogSink,RotatingFileSink,Level}` / `Objects/Extensions` /
  `Models/{Base,Inode,Data,Chunk,AuditContext,AuditOp,SettingLogging{Cycle,Kind,Output},PgfsAcl (canonical)}` /
  `Utility/{Fn,Indexer,Json,PathParser,Pg,Retry,String,NameNormalizer}` plus the shared part of `Utility/ServiceResolver`.
  Note: the only thing in `Models/` that does **not** go to Core is **`PosixAcl.cs`** (-> Pgfs.Fuse). `AppInfo.cs` was missed in the first cut.
- **Pgfs.Fuse**: the new libfuse binding (in-house) plus `mount/FileSystem.cs` plus `mount/UserResolver.cs` plus
  `Models/PosixAcl.cs` (the POSIX ACL projection) plus the posix native `ServiceResolver` (`getservbyname`@libc).
- **Pgfs.Dokan**: `assign/FileSystem.cs` (`IDokanOperations2`) plus `assign/FileSystemUtils.cs` plus `assign/WindowsUserResolver.cs` plus
  `assign/Logger.cs` (**confirmed Dokan-specific** = it implements `DokanNet.Logging.ILogger` and handles `NativeMemory<char>`) plus
  the win native `ServiceResolver` (`getservbyname`@ws2_32).
  Note: when WinFsp is added later, **everything but `FileSystem.cs`** ({`FileSystemUtils`, `WindowsUserResolver`, win_attrs}) is extracted into `Pgfs.Windows` (point 3).
- **The tools (thin exes)**: mkfs (`Initializer` + `Program` -> Core) / mount (`Program` -> Fuse + Core) / assign (`Program` -> Dokan + Core).

#### Where the `#if` and the OS branches live (what the split absorbs; grepped against the actual files)
**The compile-time `#if WINDOWS` exists in `ServiceResolver.cs` alone** = the heart of "retiring `#if`". The
rest are run-time `OperatingSystem.Is*` branches.
- `Utility/ServiceResolver.cs` `#if WINDOWS` (x6) = the native `getservbyname` (ws2_32 versus libc). -> the shared part in Core, the native part in each mechanism layer (point 4).
- `Config/Schema.cs` `IsWindows()?"P:":"/mnt/pgfs"` (the default mount point, a run-time ternary) -> each mechanism layer supplies the default to Core (point 5).
- `Config/ConfigLoader.cs` `if(!IsLinux())` (the mount(8) helper-context check through `/proc/<ppid>/comm`) -> **it stays in Core** (a run-time guard, benign off Linux). As a matter of mount(8) practice it is closer to a Fuse/mount-exe concern, so if it is ever carved out it goes to the mount side (an open detail).
- The `#if DEBUG` in `Logging/ILogger.cs` is **OS-independent** (a build configuration). -> it stays in Core. **"Core has zero `#if`" means "zero OS `#if`"** (a DEBUG condition is allowed).
- The `OperatingSystem.IsWindows()` guards in each `Program.cs` (pointing mount and assign at each other) stay inside each exe.

### The naming convention - file names, assemblies and namespaces

**Two separate knobs are used** (the current csprojs already do this): the output file name is `AssemblyName`
(lower case `{role}.pgfs`) and the C# namespace is `RootNamespace` (PascalCase `Pgfs.{Role}`). In .NET "the
assembly name is the output file name" is **one and the same knob**, so note that **a PascalCase `Pgfs.X` is a
namespace or project name and, strictly, not the assembly name** (= lower-case files and Pascal namespaces
coexist through the `AssemblyName`/`RootNamespace` separation).

| The output file (= `AssemblyName`) | The namespace (= `RootNamespace`) | Kind | The OS contract |
|---|---|---|---|
| `core.pgfs`(.dll) | `Pgfs.Core` | lib | Free (cosmetic; in a single-file publish it is embedded in the exe and disappears) |
| `fuse.pgfs`(.dll) | `Pgfs.Fuse` | lib | Free |
| `dokan.pgfs`(.dll) | `Pgfs.Dokan` | lib | Free |
| `mkfs.pgfs`(.exe) | `Pgfs.Mkfs` | exe | The `mkfs` convention (`{action}.{fstype}`) |
| `mount.pgfs`(.exe) | `Pgfs.Mount` | exe | **The `/sbin/mount.<type>` contract of `mount(8)`/fstab (the name is mandatory)** |
| `assign.pgfs`(.exe) | `Pgfs.Assign` | exe | Free (Windows has no dispatch convention) |

- **The rule**: `Pgfs.{X}` <-> the file `{x}.pgfs` (all lower case). A lower-case assembly name causes no
  trouble for reference resolution (proven by the current `lib.pgfs`).
- **`lib.pgfs` is renamed to `core.pgfs`** (with the Lib-to-Core split, in v0.2.0).
- **The lower-case names `mount.pgfs` / `mkfs.pgfs` are mandatory** (the Unix `{action}.{fstype}` convention;
  a contract, not a coincidence).
- **Tidying up the `pgfs.assign` spelling**: the build output has been `assign.pgfs` from the start (the
  `AssemblyName` in [Assign.csproj](../../src/assign/Assign.csproj)). `pgfs.assign` was only an inconsistency
  in the prose, and it is now unified to `assign.pgfs`.

### The points to settle
**Status**: all seven are settled (and audited against the actual files). Points 1 to 3 are the heavy design
decisions, 4 to 7 the light ones.
1. ✅ **Decided: the Linux layer is named `Pgfs.Fuse`** (a mechanism name, symmetric with `Pgfs.Dokan`). The `Pgfs.Posix` proposal was rejected.
   - **Why**: consistent with decision 2's "name them after the mechanism and make them swappable". macOS can share `Pgfs.Fuse` as long as it is libfuse-family (macFUSE / fuse-t). If a non-libfuse POSIX mechanism is ever needed, it is added as **a sibling assembly**, as on the Windows side with `Pgfs.WinFsp` (a POSIX common layer is not built in advance = YAGNI).
2. ✅ **Decided: "the mechanism is a lib, the tool is a thin exe"**. The same shape on each operating system: {`Pgfs.Fuse` + `mount.pgfs`} / {`Pgfs.Dokan` + `assign.pgfs`}.
   - **Why**: it keeps the command name loosely coupled to the mechanism -> swapping `Dokan` for `WinFsp` can be done **with the command name unchanged** (satisfying the original motivation for splitting by mechanism). With the alternative of "make the tool exe itself the mechanism layer", the name the user types would split, as in `Pgfs.WinFsp.exe`.
   - **The dependencies run one way**: `the tool exe -> the mechanism lib (Fuse/Dokan) -> Core`. Fuse and Dokan are not "independent" but swappable units sitting **on top of** Core.
   - **The tool exe's responsibility is being the adapter to the OS's calling conventions**: the argv conventions (swallowing the mount(8) flags, the positional arguments, deciding the helper context) / daemonizing (splitting the child process, restarting itself through `Environment.ProcessPath`) / the install name / filling in PATH. None of that is the mechanism (the libfuse ops) or Core (OS-independent SQL), so it is **a concern of its own** and does not disappear however thin it gets. `mount.pgfs` also carries the `/sbin/mount.<type>` contract of `mount(8)`/fstab (= its name is mandatory) ([fstab-support.md](fstab-support.md)).
   - **What ships**: a single-file publish embeds the mechanism lib and Core into the exe, so **what ships is still the single file `mount.pgfs` / `assign.pgfs`** (no packaging regression; consistent with decision 1's self-contained shipping).
3. ✅ **Decided: share `Pgfs.Dokan` for now and extract when WinFsp is added (YAGNI)**.
   - **The evidence**: SID/ACL/`win_attrs`/`WindowsUserResolver`/`FileSystemUtils` are **not Dokan-specific**
     (they use no DokanNet types, only `System.Security.Principal` plus `advapi32` plus Core's
     `NameNormalizer`/`Logger`). But their consumer, `FileSystem` (`IDokanOperations2`), lives in the Dokan
     layer, so with one mechanism today sharing is the cheapest.
   - **What gets extracted (when WinFsp is added later)**: **everything but `FileSystem.cs` (the Dokan binding)**
     goes into `Pgfs.Windows` (a thin OS common layer) that both `Pgfs.Dokan` and `Pgfs.WinFsp` reference.
     The block to carve out = {`WindowsUserResolver` + `FileSystemUtils` (BuildSecurity/ApplySecurity/ToAttributes/IsWritable) + win_attrs}.
     What stays in `Pgfs.Dokan` is `FileSystem.cs` plus the `Logger` adapter.
   - **The exe proposal (`Pgfs.Assign`) was rejected**: the consumer `FileSystem` would have to look up at the
     exe, which is a cycle, and it would force injecting `IUserResolver` and break the thin-exe responsibility
     (OS calling conventions only). The interface would also leak, being uid/gid on Linux and a SID on Windows.

**Points 4 to 7 (the light ones): settled on the recommended default after auditing the actual files**:
4. ✅ `ServiceResolver`: the interface in Core (the known-services table plus the `/etc/services` parsing), with the native `getservbyname` implementation (ws2_32 / libc) injected from each mechanism layer. The `#if WINDOWS` is removed in favour of the assembly boundary (= the heart of "retiring `#if`").
5. ✅ The default mount point in `Schema` (`IsWindows()?"P:":"/mnt/pgfs"`): each mechanism layer supplies the default to Core, and the OS ternary disappears from Core.
6. ✅ `assign/Logger.cs` -> **Pgfs.Dokan**: confirmed to be a Dokan-specific adapter, implementing `DokanNet.Logging.ILogger` and handling Dokan's `NativeMemory<char>`.
7. ✅ mkfs: a thin tool referencing Core alone (`Initializer` + `Program`, independent of FUSE and Dokan). Minimal change.
