# 名前空間の方針 — 見え方と実体がずれる 3 件をまとめて決める

> **道順**: [docs/README.md](../README.md) › **本書**
>
> **この doc が正である範囲**: **名前空間の見え方と実体がずれる件の方針**。
> どの名前を作れるか / 作ったものがどう見えるか / 見えているものに到達できるか。
> **3 件 (`.fuse_hidden*` の隠蔽 / Windows の予約名 / 末尾の空白・ドット) をまとめて扱う。**
>
> **隣接する doc とその担当範囲**:
>
> | doc | そちらに書くもの |
> |---|---|
> | [handle-context.md](handle-context.md) | **なぜ `.fuse_hidden*` を隠すことにしたか** (§代案 H)。`hard_remove` を立てなかった経緯 |
> | [windows-parity.md](windows-parity.md) | Windows 固有の実測 (§名前空間の先行試験) と Dokan の as-built |
> | [../Assign.md](../Assign.md) / [../Mount.md](../Mount.md) | 利用者向けの挙動と契約 |
> | [../Pgfsctl.md](../Pgfsctl.md) | `pgfsctl prune` が何を掃除するか |

## この doc を作った理由

**3 件はバラバラに決めると整合しない。** どれも「**名前空間の見え方と実体がずれる**」形で、
**片方の OS の都合で穴を開けると、もう片方から見て不可解になる**という同じ構造を持つ。
1 件ずつ直すと、**片方を塞いだ結果もう片方が開く**ことが起きる (実例は §M-1 の案 H-2)。

## 現状 (すべて 2026-09-21 に Windows 実機で実測)

| # | 件 | 見え方 | 実体 | 誰が穴を開けているか |
|---|---|---|---|---|
| **M-1** | `.fuse_hidden<16 hex>` を列挙から外している | `ls` に出ない | DB に行がある | **pgfs 自身** (意図的に隠している) |
| **N** | Windows の予約名 (`CON`/`PRN`/`NUL`/`AUX`/`COM*`/`LPT*`) を作れる | 列挙に出る | ある | **Win32 層** (デバイス名として解決する) |
| **T** | 末尾の空白・ドットを持つ名前を作れる | 列挙に出る | ある | **Win32 層** (パス正規化で落とす) |

### M-1 — 列挙に出ないのに消せない

**これは「漏れ」ではなく、[handle-context.md §代案 H](handle-context.md) で
意識的に受け入れた代償である。** 当時の記述:

> **代償**: **列挙に出ないのに `rmdir` が `ENOTEMPTY` になる**ことがある (隠しファイルが残っている親)。
> **見た目は空なのに消せない**ので、迷ったら `prune` を撃つ。

**ただし Windows での実測は、この代償の記述より重い**:

| 操作 | 結果 |
|---|---|
| `Get-ChildItem -Force` | **空** (= 代償のとおり) |
| `Test-Path` / `ReadAllText` (名前を直接指定) | **見える・読める** |
| `Remove-Item` (名前を直接指定) | **「指定されたファイルが見つかりません」で失敗** ← **doc に無い** |
| `[System.IO.File]::Delete` (Win32 `DeleteFile` 直接) | **消せる** |
| `Remove-Item <親>` (rmdir) | **「ディレクトリが空ではありません」で失敗** (= 代償のとおり) |

**`Remove-Item` が効かないのは、PowerShell のプロバイダが親を列挙してから消しにいくためと考えられる**
(挙動からの推測・未確認)。**エクスプローラも列挙ベースなので同じはず**である。

つまり Windows の利用者から見ると:

- **見えない / 普通の手段では消せない / ディレクトリも消せない**
- **名前を一字一句知っていて、かつ Win32 API を直接叩ける手段があれば消せる**

**「消せない」より「消す方法があるのに誰も辿り着けない」ほうが運用では厄介**である。
**`prune` を撃てば消えるが、「見えないものが残っている」ことに気づく導線が無い。**

### N — 予約名

**`CON` / `PRN` / `NUL` / `AUX` / `COM1` / `LPT1` はすべて作成でき、`CON` / `COM1` は Win32 パスでも読める**
(ドライブ配下なので DOS デバイス解決が効かない)。**`NUL` だけは Win32 経由で NUL デバイスに化け、読むと空**が返る。

**実害**: **`NUL` という名前のファイルを 1 つ作ると、そのディレクトリが `Remove-Item -Recurse` で
消せなくなる** (`ERROR_INVALID_FUNCTION`)。回収には `\\?\` 経由の個別削除が要る。

### T — 末尾の空白・ドット

**`dot` と `dot.` が別物として共存でき、Win32 パスで `dot.` を指定すると正規化されて `dot` の中身が返る。**

**実害**: **エラーにならない。** 利用者は**誤ったデータを読んだことに気づけない**。
**3 件の中でいちばん静かで危ない。**

## 案と trade-off

### M-1 (`.fuse_hidden*` の隠蔽)

| 案 | 内容 | 得るもの | 失うもの |
|---|---|---|---|
| **H-1** | **現状維持** + Windows の実害を doc に追記 | 変更なし。**既に受け入れた代償のまま** | Windows の利用者は**気づく導線が無い**ままになる |
| **H-2** | **`IsDirectoryEmpty` を隠す側に揃える** (隠した行を数えない) | **両 OS で `rmdir` が通る** | **隠れた inode が親ごと消える** = 孤児 data が増え、**「消えた」ことが誰にも見えない**。**prune で回収はできるが、消えた事実が残らない** |
| **H-3** | 隠したまま、**`rmdir` が失敗したときにログで理由を伝える** | 利用者が `prune` に辿り着ける | **エラーコードは変わらない**ので、GUI / エクスプローラからは依然として理由が見えない |
| **H-4** | **Dokan 経路では隠さない** (Core の判定に OS 条件を入れる) | **Windows の実害が全部消える** (見える・消せる・rmdir も通る)。**Windows では libfuse が残骸を作らないので、隠す理由がそもそも無い** | **同じ FS を両 OS からマウントすると見え方が変わる**。Linux 側の代償は残る。**当時「実害」と評価した「他マウントの `ls` に残骸が出る」が Windows 側で復活する** (下 [§当時の決定](#当時の決定とその前提がいまどうなっているか)) |

**H-2 が「片方を塞ぐともう片方が開く」の実例である** — `rmdir` は通るようになるが、
**C-2 (名前が消えても開いている間は実体を生かす) が守ろうとした実体を、気づかないうちに消す**。

### N (予約名) / T (末尾の空白・ドット)

**2 件は同じ形なので同じ案立てになる。**

| 案 | 内容 | 得るもの | 失うもの |
|---|---|---|---|
| **P-1** | **現状維持** (通す) | **Linux と同一 namespace**という設計目標をそのまま守れる | Windows から**消せないもの / 黙って別物が開くもの**を作れる |
| **P-2** | **Windows からの作成だけ弾く** (Dokan 層で `CreateFile` を `STATUS_OBJECT_NAME_INVALID` にする) | **Windows から新たに不可解なものを作れなくなる**。**Linux が作ったものは見える・読める**ので同一 namespace は保たれる | **非対称**になる (Linux から作れて Windows から作れない)。ただし**非対称性は Win32 側に既にある** |
| **P-3** | **FS 全体で弾く** (Core で作成時に拒否) | **どちらの OS からも同じ名前空間**になり、保証が強い | **Linux が不便になる** (POSIX 的には正当な名前を拒否する)。**既存 FS に既にある名前をどうするかの移行問題**が出る |

**P-3 は「Linux と同一 namespace」の目標と正面から衝突する** — 揃えるために
**両方を Windows の制約に合わせる**ことになるため。

## 決定

**M-1 = H-4 / N = P-2 / T = P-2 を採用する。** 判断の言葉は
**「Windows の仕様なので (推奨の) とおりで」** — **3 件とも Windows 側の事情から来ている穴なので、
Windows 側で塞ぐ**という整理である。

**下は提案時の推奨文で、そのまま決定の理由になっている。**

**理由は 3 件に共通して 1 つ**:

> **穴を開けている主体のところで塞ぐ。**

- **M-1 の穴は pgfs 自身が開けている** (隠している)。**Windows では隠す理由が無い**
  (libfuse が `.fuse_hidden*` を作らないため) ので、**そこで隠すのをやめれば実害が消える**。
  **Linux 側の代償は残る**が、それは **`hard_remove` を立てられない libfuse の制約から来ている**ので、
  **pgfs 側で消せる穴ではない** ([handle-context.md §なぜ `hard_remove` を立てないか](handle-context.md))。
  **この案は当時の評価を覆すことを承知のうえで推している** — 当時は「他マウントの `ls` に出るのが実害」
  と見て両 OS に効かせた。**実測後は「見えないほうが実害」に見える**が、**そう見えるのは
  「`ls` に残骸が出る」を軽く見ているだけかもしれない**。**ここが推奨のいちばん弱い部分**なので、
  **判断する人は [§当時の決定](#当時の決定とその前提がいまどうなっているか) の対比表を見てほしい。**
- **N / T の穴は Win32 層が開けている。** **Win32 の制約は Windows 側にしか無い**ので、
  **Windows からの入口で弾く**のが素直である。**Linux 側に持ち込む理由が無い。**

**この方針だと「Linux が作った予約名を Windows から消せない」は残る。** これは**意図的に残す** —
**弾いても問題が移動するだけ**で、消えはしないため。**残すなら doc に書く**のが本書の役割になる。

### 実装の規模 (見積り)

| | 触る場所 | 規模 |
|---|---|---|
| **H-4** | `Api.ListChildren` の隠蔽判定に OS 条件を渡す (Core)。呼び出し側は Fuse / Dokan | **小**。判定は既に `IsLibfuseHidden` に集約済み |
| **P-2 (N)** | Dokan の `CreateFile` で名前を検査 (`src/dokan`) | **小**。予約名の一覧は固定 |
| **P-2 (T)** | 同上 (末尾の空白・ドットを検査) | **小** |

**どれも Dokan 側の担当範囲で完結する** (`Api.cs` / `src/dokan`)。
**H-4 だけ Core の `ListChildren` を触る**ので、**Fuse 側の呼び出しに影響が無いことを FUSE 側に確認してもらう。**

### 受入条件

| 案 | 確かめること |
|---|---|
| **H-4** | Windows: `.fuse_hidden<16 hex>` が**列挙に出る / `Remove-Item` で消せる / 親が `rmdir` できる**。Linux: **従来どおり隠れる** (回帰なし) |
| **P-2 (N)** | Windows: `CON` 等の作成が**拒否される**。**Linux から作った同名は Windows で見える・読める** |
| **P-2 (T)** | Windows: `trail ` / `trail.` の作成が**拒否される**。**既存のものは見える** |

**いずれも「修正前ビルドに当てて落ちること」を確認してから land する**
([tests/windows/README.md §テストを書くときに踏んだ罠](../../tests/windows/README.md))。

## 当時の決定と、その前提がいまどうなっているか

**M-1 を「両 OS に効かせる」と決めたのは意識的である。** [handle-context.md §代案 H](handle-context.md) の理由:

> **Core に置いたので両 OS に効く** — 実害は「**他マウントの `ls` に出る**」ことで、
> その他マウントには Windows も含まれるため。

**この理由自体は今も成り立つ。** 変わったのは**比較の対象**である:

| | 当時の評価 | 実測後 |
|---|---|---|
| **隠す**ときの実害 | 「`rmdir` が `ENOTEMPTY` になることがある。迷ったら `prune`」 | **+ Windows では普通の手段でファイル単体すら消せず、何が邪魔しているかも分からない** |
| **隠さない**ときの実害 | **他マウント (Windows を含む) の `ls` に残骸が出る** | 同じ |

**当時は「見えるほうが実害」と評価した。実測後は「見えないほうが実害」に見える** —
ただし**それは「残骸が `ls` に出ること」を軽く見ているだけかもしれない**ので、両方を並べておく。
**H-4 (Dokan では隠さない) を採ると、当時「実害」と呼んだものが Windows 側で復活する。**

**前提のうち 2 つは、当時の検討に入っていなかった** (FUSE 側の確認):

1. **「迷ったら `prune` を撃つ」の重さ。** `pgfsctl prune` は **Windows でも動く** (本日 何度も実行して確認)
   ので「撃てない」わけではない。**ただし prune は生きているマウントが 1 つでもあるとデータを消す側を
   丸ごと飛ばす**ので、**全マウントを止めてから撃つ**必要がある。**「迷ったら撃つ」ほど軽い操作ではない。**
2. **`.fuse_hidden*` は libfuse が作るもの、という前提だった。**
   **利用者が同じ書式 (`.fuse_hidden` + 16 桁 16 進) の名前を自分で付ければ、Windows でも同じ状態になる。**
   `IsLibfuseHidden` は**書式だけで判定し、誰が作ったかを区別しない**ため。**この形は当時評価されていない。**

## 外してはいけない線 (当時の決定・踏むと壊れる)

- **`GetByPath` (パス解決) からは隠さない。** 外すと**その fd を生かしている当のマウントが、自分の
  隠しファイルを引けなくなる** — libfuse は**隠し名で `getattr` / `release` を撃つ**ため。
  **「隠すならどこでも隠す」で揃えると壊れる。** 隠すのは**列挙 (`ListChildren`) だけ**である。
- **`hard_remove = 1` は採らない。** `.fuse_hidden*` をそもそも作らせない案はここで一度潰れている
  ([handle-context.md §なぜ `hard_remove` を立てないか](handle-context.md))。**再提案するなら当時の理由を読んでから。**
- **`IsDirectoryEmpty` を隠す側に揃えるなら、C-2 が守っている実体を消さない手当てが要る** (上の H-2)。

## 却下した案

- **`.fuse_hidden*` を DB から消す / 作らせない** — **libfuse が作るものなので pgfs 側では止められない。**
  `hard_remove = 1` を立てれば作られなくなるが、**立てると `unlink` 後の read と rename-over が壊れる**
  ([handle-context.md](handle-context.md) で①まで行って戻ってきた記録がある)。
- **予約名を自動リネームする** (`CON` → `CON_` 等) — **DB 名を自動で書き換えない**という既存方針に反する
  ([windows-parity.md](windows-parity.md))。**Linux から見た名前が勝手に変わる**のは同一 namespace を壊す。
