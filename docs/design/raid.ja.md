## 動機 / アイデア

複数の PostgreSQL を指定し、**全部をまとめて 1 つの pgfs ファイルシステム**として使う。

- ストライピング (1 ファイル = 1 エントリを分割) は **しない**。**ファイルパス単位**で、どこかの DB に丸ごと置く。
- 各接続先 DB は **構成を完全に無変更** = それぞれが通常の pgfs インスタンス (同一スキーマ / prefix、単体でもそのままマウント可能)。
- ねらい: **容量の水平加算 (RAID0 的)** と **冗長化 (RAID1 的)** を、バックエンド DB に一切手を入れず **アプリ層 (mount/assign) のファンアウトだけ**で実現する。

## 全体像 — どう実現するか

現状の依存は `tool exe → 機構層 (Fuse/Dokan) → Api → 1 PostgreSQL`。RAID 化はここに **集約層を 1 枚挟む**だけ:

```
            ┌─────────────────────────────────────────┐
 FUSE/Dokan │  RaidApi  (Api と同じ表面を実装)          │
   (無改造) │  各 FS 操作 = ファンアウト + マージ        │
            └───┬───────────┬───────────┬─────────────┘
                │           │           │
             Api(子1)    Api(子2)    Api(子3)      ← 各々ふつうの pgfs
                │           │           │
              PG #1       PG #2       PG #3        ← 構成無変更・単体マウント可
```

- **`RaidApi` (仮称)** を [Api](../../src/core/src/Api/Api.cs) と同じ表面で実装し、子 `Api[]` を束ねる。FUSE/Dokan 層は単一 `Api` を見ているつもりのまま動く (依存方向不変)。
- 各子 Api は独立した pgfs DB。**スキーマ / prefix / DDL は無変更**なので、RAID を解除すれば各 DB はそのまま単体 pgfs として使える。
- 設定は `database.connection` を **複数**受ける + RAID パラメータ (下記)。Citus ([support_for_citus.ja.md](support_for_citus.ja.md)) とはレイヤが直交し、各子 DB が単体でも Citus でも構わない。

## 配置と複製数 (新規作成・書き込み時)

RAID モードの追加パラメータ **複製数** (仮 `raid.replicas`)。**未指定時の既定は 1**。配置の基準は各 DB の [`pgfs_statfs()`](df-support.ja.md) の実空き容量。

| 値 | 相当 | 新規ファイルの配置 |
|---|---|---|
| **0** | RAID0 | 1 コピーを **空き容量が最小の DB** に作る (= 1 台を詰めてから次へ溢れさせる pack 戦略) |
| **1〜n** | n-way 複製 | 空き容量が最小の DB から**順に n 個**選んでコピーを作る。`n` が DB 数以上なら **-1 と同義** |
| **-1** | RAID1 | **すべての DB** にコピーを作る |

- 既定 `1` = 1 コピー。配置は「1〜n」モードの `n=1`。
- 「空き容量が最小に置く」は意図的に **spread ではなく pack** (断片化を避け、空き容量の大きい DB を将来の大ファイル用に温存する読み筋)。

## 名前空間マージ (読み込み時の見え方)

N 個の DB のツリーを 1 つにマージして見せる。あるパスに対し、全 DB から同一パスのエントリを収集して:

- **内容同一の判定**: `更新日時` と `ファイルサイズ` が一致するエントリは **同じもの (= 複製)** とみなし、**1 つに畳む**。
- **ディレクトリは例外**: `更新日時` が違っても、同名なら **同一ディレクトリ**とみなす (子の union を見せる)。
- **分岐 (内容が異なるコピー) が複数ある場合**:
  - `更新日時 desc, ファイルサイズ desc` で **最も新しいものを正** (素のパスで見せる)。
  - 残りは末尾に `~1`, `~2`, … の **サフィックス**を付けて見せる (新しい順)。
  - サフィックス採番時、**既存エントリと衝突する番号はスキップ** (実在の `name~1` を踏まないよう、空き番号を使う)。

→ 競合コピーを隠さず全部見せる方針 (Dropbox の "conflicted copy" 的)。複製どうしは 1 つに見える。

## 書き込み時

- 読み込み時に**サフィックスを付けていた (= 競合があった) 場合、その状態で実体を全部リネーム**する (競合の曖昧さを名前として永続化し、見え方を固定する)。
- 論理ファイルの **エントリ数 < 複製数** なら、新規作成時の配置ルールで複製先を追加で選び、内容を複製する (書き込みを契機に**目標冗長度へ自己修復**)。
- **すべての (複製) エントリに対して同じ書き込み操作**を適用する (ミラー書き込み)。

## OS へ通知する空き容量 (statfs / df)

- 全 DB の中で **最も空き容量の多いもの**を返す (楽観的 = 「まだ最低これだけは書ける」)。各 DB の空きは [df-support.ja.md](df-support.ja.md) の `pgfs_statfs()` をそのまま流用。

## 進める上で気にする点 (要検討 / Open Questions)

実現の道筋は上のとおり。詰めるべきはおおむね次の 9 点。どれも「やらない理由」ではなく「決め事」。

1. **`0` と `1` の差**: 現記述では「0 (RAID0)」も「既定 1」も *空き最小の 1 台に 1 コピー* で配置が同じ。`0` を別意味 (例: 純粋ラベルとしての「冗長ゼロ」/ あるいは将来のストライプ余地) にするか、`1` のエイリアスとして畳むか。
2. **複製の原子性 / 部分失敗**: N 台中 k 台だけ書けて落ちた時。複製間で mtime/size がズレ → 次回 read で「競合 = `~N`」に化ける。これを **許容 (競合として顕在化)** するか、ベストエフォート再同期を入れるか。
3. **`mtime+size 一致 = 内容同一` の仮定**: 偶然一致による誤マージのリスク。`pgfs_data` の指紋 (ハッシュ列) を併用するか、仕様どおり mtime+size で割り切るか。
4. **クロス DB の一貫性 / ロック**: 既存の [`pgfs_lock`](support_for_citus.ja.md) は単一 DB 内。N DB にまたがる rename / 書き込みの直列化は別建てが要る (または ②の競合顕在化で吸収)。
5. **読み取りコスト**: `lookup` / `readdir` ごとに N 台へファンアウト + マージ。集約層の InodeCache、readdir の N-way マージコスト、片肺 (一部 DB 不達) 時の挙動。
6. **競合サフィックスの安定性**: `~N` は「どの DB が今生きているか」で read のたびに揺れうる。write で実体リネームして固定する設計だが、**read のみのアクセス中の見え方の揺れ**をどう扱うか。
7. **`st_ino` / ハードリンク**: パス単位配置だと DB 跨ぎの inode 共有は不可。マージ後の `st_ino` を **DB 跨ぎで一意**にする採番が要る (`id` に DB インデックスを混ぜる等)。
8. **削除 / rename のファンアウト**: 全複製への伝播。競合 (`~N`) を持つパスの削除・移動のセマンティクス。
9. **設定表現**: 複数 connection + 複製数を CLI / TOML でどう書くか ([settings-matrix.ja.md](settings-matrix.ja.md))。各子 DB で schema / prefix 差異を許すか。

## 現行設計との足場 (流用できるもの)

- **空き容量**: [df-support.ja.md](df-support.ja.md) の `pgfs_statfs()` を配置判断と statfs 報告の両方に流用。
- **無改造で済む層**: 集約層が `Api` 表面を保てば [Mount.ja.md](../Mount.ja.md) / [Assign.ja.md](../Assign.ja.md) (FUSE/Dokan) は手を入れない。v0.2.0 の機構層分割 ([v0.2.0-plan.ja.md](v0.2.0-plan.ja.md)) で Core が OS 非依存に整理済なので、`RaidApi` は Core 内に素直に収まる。
- **各 DB 無変更**: Citus との直交。子 DB を単体 / Citus どちらの構成にもできる。

## 一般化: バッキングストア非依存の union+複製レイヤ (着想続き)

> **まだ妄想段階。決定事項ではない。** 上の「複数 PostgreSQL RAID」を一般化したら *PGFS である必要すらない* ことに気づいた、という思考メモ。

### 気づき

集約レイヤ (`RaidApi`) は **子が何で裏打ちされているかを問わない**。今は子 = `Api` (PostgreSQL) に縛っているが、子を **「バッキングストア」抽象**に持ち上げれば、ファンアウト + マージ + 複製のロジックはそのまま、裏が PG でなくてよい。

```
RaidApi → IBackingStore[]
            ├─ PgfsBackingStore   (= 現 Api / PostgreSQL)
            ├─ PassthroughStore   (= ただのディレクトリ / マウントポイント。System.IO 直叩き)
            └─ … (将来: S3 風オブジェクトストア等)
```

- **全部 PG** → 上の「複数 PostgreSQL RAID」(現行スケッチ)。
- **全部 ただのディレクトリ** → **PG ゼロの汎用 union+ミラー FUSE** (= "PGFS である必要すらない")。
- **混在** → 後述「メタデータ面 / データ面の分離」。

### なぜそのまま乗りやすいか

現行スケッチの判定が既に **最小公倍数のメタデータ**しか前提にしていない:

- 複製の同一判定 = **mtime + size** (§名前空間マージ) → exFAT 等のダンボ FS でも取れる。
- 配置基準 = **空き容量** (`pgfs_statfs`) → ただのディレクトリなら `statvfs` / `DriveInfo` で取れる。

pgfs 固有 (xattr / ACL / st_ino 共有 / ハードリンク) に依存しない範囲で組まれているので、ダンボ backing へ移植しやすい (設計が先回りで最小公倍数だった)。

### 使い道 (妄想)

- **RAID1 (複製数 -1 / 2) = メディア複製ツール**: 2 ディレクトリへライブミラー。write 契機の自己修復 (§書き込み時) が rebuild になる。
- **USB メモリ 10 本を各々 exFAT + 複製数 2 = 即席バックアップ + 分散 FS**: mergerfs+SnapRAID 的な寄せ集めディスク NAS を、リアルタイム複製で。
- **メタデータ面 = PG (pgfs) / データ面 = ダンボディスク**: exFAT は owner/mode/xattr/symlink/hardlink を持てない (mtime+size は持てる)。POSIX メタデータ・複製カタログ・st_ino 採番を **pgfs (PG) を 1 枚カタログとして混ぜて**権威化し、実体は USB 群に分散 + 複製。Ceph (MDS+OSD) / HDFS (NameNode+DataNode) と同型 — **pgfs は FS 全体ではなくメタデータ DB として一番強い所だけ担う**。

### Citus 不要説 (容量観点限定)

この FS の上に **PostgreSQL のデータディレクトリ**を置けば、単一 PG でも多数ディスクの**容量を水平加算**できる → *容量目的だけ*なら Citus 不要。

- 補足: PG は元々 **tablespace** で複数ディスクに分散可。union FS の利点は「1 マウントへ透過化 + 複製も込み」。
- 置き換え**ない**領域: 計算 / スループット (単一 PG = 1 プロセス・1 WAL・単ノード CPU/RAM/IO)、マシン跨ぎ HA、分散並列クエリ。= **容量 ≠ 性能**。
- **循環注意**: RAID 層自体を pgfs (PG) にすると PG-on-FUSE-on-PG で自滅。データディレクトリを載せる用途では RAID 層は **ダンボ FS over 実ディスク**に限る (非循環)。

### 近い既存システム (= 設計空間の裏付け)

mergerfs (pooling) / SnapRAID (異種ディスクのパリティ) / git-annex `numcopies` (複製数) / Ceph・HDFS (メタ面とデータ面分離)。本案 = 「pooling + リアルタイム n-way 複製 + 競合コピー (`~N`) 和解 + 任意で PG メタデータ権威」を 1 個のユーザ空間 FS に、という位置づけ。

### 追加で詰める点 (一般化で増える Open Questions)

上の 9 点に加えて (いずれも妄想段階の決め事候補):

10. **バッキングストア抽象**: `IBackingStore` の表面 (CRUD + statfs + capabilities) の切り方。`PgfsBackingStore` と `PassthroughStore` の最小共通項。
11. **機能ケイパビリティ**: backing ごとに xattr/ACL/symlink/hardlink 可否が違う → `Capabilities` で表現し `RaidApi` が degrade (持てない backing はメタデータ面で補完 or 機能落ち)。
12. **メタデータ面の所在**: ダンボ backing の POSIX メタ・複製カタログ・st_ino 採番を PG カタログ / サイドカー / 諦め のどれで持つか (二面構成案)。
13. **DB-on-FUSE の fsync / 順序保存**: データディレクトリ用途では PostgreSQL の fsync 誠実さ・書き込み順序・クラッシュ時の部分複製耐性が成否を分ける一点 (exFAT は耐久弱)。
14. **RAID1 ≠ バックアップ**: ライブミラーは削除も伝播 → 誤削除/ランサムには無力 (ディスク故障には強い)。trash / 版管理を別レイヤにするか。競合コピー `~N` は部分的セーフティネット。
15. **ホットプラグ / degraded / rebuild**: USB 抜去時の縮退読み + 復帰/追加時の再複製。failure-domain を意識した配置。
16. **設定表現の拡張**: 子が「接続文字列 (PG)」か「ディレクトリパス」かの混在記法 (§9 の拡張)。
